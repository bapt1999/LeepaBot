User Profile and Objectives
The background is a personal engineering journey driven by curiosity for AI behavioral architecture, context routing, and stateless cognitive pipelines. The primary goal is to build a highly conversational, context-aware, autonomous Discord chatbot that actively participates in discussions, shitposts, and organically reacts to the channel vibe without needing direct command prompts.

Core Architectural Features
The host uses the Python discord library, deployed 24/7 on a Google Cloud Platform e2-micro Linux server using a systemd background daemon. The external AI engine utilizes a multi-provider multiplexer supporting Gemini, Groq, DeepSeek, and OpenRouter. Sensitive data is secured in an environment file. The logic layer routes messages based on engagement levels through a probability filter. Prompts and data are decoupled from routing logic to ensure clean separation of concerns.

Phase 1: Foundation and Interface
The bot establishes a reliable Discord connection, separating event handling from core business logic. This phase ensures the basic skeleton can send and receive messages while maintaining thread safety for asynchronous operations. Early hardcoded test commands (such as !ping) that lived directly in the entry point have been removed; the entry point is now a thin event forwarder and all behavior lives in the logic layer.

Phase 2: Social Cognition and Routing
The bot utilizes a single-track engagement router handling Direct, Quoted, and Ambient mentions. Direct and Quoted engagement always triggers the LLM; Ambient messages pass through a low-probability filter, further penalized when the message originates from a rival bot.
[HISTORICAL NOTE] Earlier versions also ran a parallel classification track that flagged content as Standard, Shitpost, Yelling, Wall of Text, or Quick Banter, and dynamically assembled tone instructions from these tags. This hand-holding relied on mediocre, made-up heuristics and has been fully removed; the LLM now reads the channel energy on its own from raw context.

Phase 3: Stateless Short-Term Memory
The bot maintains isolated Short-Term Memory queues for unique channel IDs. When the queue reaches capacity, a non-blocking background task compresses logs into a dense running summary. Infrastructure states (rate limits, timeouts) are intentionally logged into the STM as internal moods, allowing the bot to acknowledge its own outages in-character and providing a live debugging trace on the server console.
[HISTORICAL NOTE] Long-Term Memory extraction and RAG pipelines have been deliberately severed to prevent toxic trait compounding and context window hijacking. The LTM took the form of contextless third-party LLM summaries stored in JSON; the bot anchored heavily to these lossy entries and its behavior degraded over time. The deprecated implementation is preserved in lore_vector_store.py but is not imported anywhere. The bot now operates statelessly across sessions, relying purely on sharp, immediate contextual awareness and a resilient baseline persona rather than historical databases.

Phase 4: Behavioral Expression and Persona
The bot utilizes a strict Chain-of-Thought Cognitive Pipeline. An internal thinking block, seeded with a randomly injected entropy word, allows the LLM to plan its comedic angle via lateral association before rendering dialogue. The persona is engineered as a highly enthusiastic, zero-ego, partner-in-crime fox-girl who acts as an enabler and peer to the users. A hard syntax limitation strictly forbids the use of question marks to ensure all responses are definitive, declarative statements. N-shot behavioral examples and the core persona are modularized in a dedicated prompts file. Physical Discord emoji reactions are decoupled from text generation and utilize a centralized, global inventory of custom emojis available across all servers. An Interception Matrix and Infinite Loop Slayer prevent dual-bot spam.

Phase 5: Thermal Tuning and Native Integration
The bot employs a centralized Thermal Tuning Matrix that maps context-specific temperature ranges to a normalized scale. A provider-agnostic translation layer scales these temperatures to model-specific limits. The Gemini integration utilizes a native REST endpoint to unlock thinkingConfig at a HIGH level. Frequency and presence penalties have been intentionally excluded to maintain compatibility with bleeding-edge preview models, relying entirely on structural prompt entropy to prevent repetition loops.

Phase 6: Infrastructure and DevOps
The system is deployed on a GCP Ubuntu instance managed by systemd. Code updates are synchronized via GitHub. For real-time monitoring and debugging, the logic layer supports raw JSON output logging directly to the terminal, allowing for live analysis of the bot's thinking blocks and internal mood states without needing to parse system journals.

Phase 7: Image Analysis
The bot is able to see images in jpg, jpeg and png types, and integrate their contents in its answers. Images are intercepted at the edge and translated into dense plain-text descriptions by a decoupled vision engine (Gemini primary, OpenRouter Llama Vision fallback) before entering the Short-Term Memory. Descriptions are generated for all incoming images, including ambient ones the bot never responds to, so that visual context is retained for later turns.
[HISTORICAL NOTE] webp support existed at one point and has been removed.
